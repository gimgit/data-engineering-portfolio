05/2026 - PresentAWS S3 · EKS · MSK · Glue · AthenaTechnical owner
Constraints

Managed-warehouse CDC apply and query costs grew with data volume. The migration had to preserve the change stream and consistency of ~200 live tables while separating physical storage, query access and lifecycle management. The platform would also take on MERGE and cleanup responsibilities previously handled by the managed engine.

1. Making the lakehouse operable

Compaction · Watermarks · S3 lifecycle · Query layout

Operating invariants

Snapshot watermarks

Replaced wall-clock lookback windows with incremental boundaries between the last processed snapshot and the current snapshot.

Table-shape rules

Used size, change rate and delete locality to choose Copy-on-Write (CoW) or Merge-on-Read (MoR) through first-match rules.

Physical deletion

Defined one deletion lifecycle: DELETE → compaction → snapshot expiry → S3 noncurrent-version expiry.

Encoding the CoW / MoR cost trade-off

OrderConditionChoice and rationale
R0Effectively append-only; changes <1%CoW: prioritize simpler reads.
R1Table size ≥1TBMoR: avoid the absolute cost of full rewrites.
R2Changes ≥10,000 rows/h AND table size ≥10GBMoR: avoid write amplification.
R3All remaining tablesCoW: avoid delete-file read overhead.
MERGE cost per run: -97%Large table: delete-locality repartitioning + static pruning
259TiB → 120TiBSnapshot expiry + object lifecycle: primary bucket -54%

Withdrawing an unsupported measurement

Evidence audit

Rechecked an earlier claim that row-group tuning had reduced scans from 6TB to 0.5TB against production event logs. Across 46 runs, scans still read 99.5-100% of the table; the row-group change itself saved nothing. Publicly withdrew the claim because a modeled estimate had been labeled as a measurement.

What the subsequent tests established

  • Traced engine source code and found that the runtime filter never reached the row-group residual, exposing an implementation gap.
  • Found that literal IN predicates enabled pruning, but lists above 200 values reverted to full scans.
  • Measured a production-shaped, 131-file / 3.92GiB slice: scan volume 3,519MB → 892MB (-74.7%); wall time 22.7s → 6.7s.
Scope · These are measurements from a single-bucket slice. A full-scale -99.9% figure is only an arithmetic estimate and is not presented as an achieved result.

Remaining operational work

Guard scans

Evaluating how to remove a target-state guard generating ~332M GET requests/day while preserving correctness.

Consumer contracts

Excluded retirement of the existing bronze-shaped table from cost-saving options because it would break the consumer data contract.

2. Spark on EKS / Karpenter compute economics | Wrtn Technologies

08/2026 - PresentEKS · Karpenter · EC2 Spot · EBS · NVMeSole analyst / technical owner
Question

After stopping a cost leak, the Spark executor fleet still cost ~$830/day, and 81% of large nodes had planned memory utilization below 45%. Was Karpenter the cause, or was workload sizing preventing efficient placement?

From symptoms to root cause

Symptoms

Oversized 8xl nodes: ~800 launches/day
Long-job launch failures: 69-82%
92% of executor decommissions truncated

→
Evidence

Heap census: 41 applications
Event logs: 775 applications
Audit logs, Spot reclamations and live Pod specifications

→
Root cause

100Gi scratch request per Pod
493Gi allocatable storage per node
Four-Pod cap, regardless of instance size

Resource-by-resource decisions

ResourceMeasurementDecision
MemoryHeap p50 of 30GiB reflected delayed GC, not demand. Peak unified-memory usage <2GiB; zero spill and OOMs.Delete-merge executor: 32g → 24g.
CPUChanging core requests from 4.0 to 3.5 alone produced no placement gain.Adjust memory and cores together by workload.
Ephemeral diskFixed 512GiB EBS volumes exposed 493GiB allocatable, capping all node sizes at four Pods.NVMe instance-store pool + EBS fallback.
Spot capacityUnlike the main pool, the long-job pool had no fallback tier.Broader instance-family fallback; prevent immediate reclamation after arrival.

Acceptance criteria before spending

Alternatives rejected through measurement

  • 1TiB gp3 NodeClass: added storage cost consumed half the gain.
  • Exclude 8xl instances: pool weights promoted 12xl instead.
  • Change pool weights: collateral impact on other workloads.
  • Another dedicated pool: replaced by a simpler tiered design.

Validation of the selected design

  • Proved the NVMe allocatable increase with a $0.02 positive-control test.
  • Used EBS fallback to cover capacity gaps in two Availability Zones.
  • Inspected live resolved configuration to find a missing production overlay hidden by a passing development test.
493 → 1,590GiBAllocatable ephemeral storage: 3.2x; four-Pod cap removed
69-82% → 26% / 2%Long-job launch failures in observed post-fallback windows
Evidence boundary · Quantified ~$2.1K/month in sparse-node overpayment, but do not claim realized savings before the day-seven validation gate. The long-job result is limited to relieved capacity starvation and verified fallback behavior; no causal wall-time improvement is claimed.

3. Kafka Connect CDC reliability | Wrtn Technologies

11/2025 - PresentAmazon MSK · Strimzi · Kafka Connect · IcebergRoot-cause analysis owner
Problem

Data movement could stop even with connector status RUNNING and consumer lag at zero. Control-plane status alone did not establish end-to-end liveness from source to target.

Three distinct silent-loss mechanisms

Failure classWhy it went undetectedRecovery and prevention
Source stallA two-day gap across 42 tables showed lag=0; discovered five months later.Introduced source-target parity and commit-age checks.
Zombie coordinator11 RUNNING connectors missed ~50.7K rows over 16 minutes.Iceberg sink runtime upgrade and anti-join recovery.
Merge-window exclusionA downstream window turned a brief stall into permanent loss.Bounded backfill and exact reconciliation across 12 tables, up to ~355K rows.

Defining end-to-end health

Commit ageDoes the latest target commit keep advancing?
Source-target parityCheck missing rows and unapplied deletes separately, not just row counts.
Idempotent recoveryUse anti-joins and natural keys to make at-least-once replay safe.
Operating rule · Zero lag can mean zero production. Status is not liveness; recovery is complete only when replay is safe and exact reconciliation passes.

Extending the checks to connector nodes

Undrainable-node root cause

  • A 30-day expiry combined with do-not-disrupt Pods caused persistent drain failure.
  • Timestamps ruled out the competing explanation that the annotation arrived too late.
  • Applied a development fix: set expiry to Never on the dedicated pool.

Regression prevented through peer review

  • Found false positives in a reaper treating two coordinator IDs within 20 minutes as split-brain.
  • Proposed a time-overlap discriminator and a leader-preservation rule.
  • Blocked automation that would restart the real leader and trigger a rebalance loop.

Ownership · Handled forensic root-cause analysis, prevention and quantified backfill verification for the three incidents. Teammates operated the systems during the incidents. The production node-pool change remains open; only the development fix is complete.

Separate delivery evidence

Built end-to-end CDC ingestion for consent data subject to regulatory requirements. Validated 12M+ document keys with zero duplicates and zero DLQ entries. Fixed a corruption mechanism that could remain invisible to the DLQ, rejecting the assumption that an empty DLQ proves health.

4. Multiregion governance IaC and security | Wrtn Technologies

01/2026 - PresentTerraform · GitHub Actions · BigQuery · IAM · Pub/SubRepository creator / technical lead
Internal users

IAM, authorized views and column classification were managed manually across 13 projects, ~314 datasets and ~100 users. The design needed consistent separation by region, environment and access tier, while letting the team extend it safely without depending on the original designer.

Separating infrastructure boundaries from policy

Region · EnvironmentProject boundary
Dataset factoryModule + tfvars
Metadata SSOTTier · schema · grants
Authorized viewsRaw access denied by default
  • Encoded persona × service group × tier × region in one Terraform source of truth.
  • One time-limited PII grant entry generates a personal view, dataset authorization and decryption permissions.
  • Used keyless CI/CD and plan history to detect console drift and establish IaC-only changes.

Human review as a security boundary

DDL eventAudit logs and Pub/Sub detect new columns.
Classification proposalAn LLM proposes a tier; unconfirmed columns remain fail-closed.
Human approvalReview risk tiers, then regenerate authorized views automatically.
What was not automated

Prohibited environment-wide auto-confirmation because it could approve sensitive columns in bulk. Human review remains a security boundary.

Reducing review bottlenecks

Applied different SLAs and validated bulk-accept paths for low-risk tiers versus tiers likely to contain sensitive data.

Adoption and results

Days estimated → ~1 hourNew-region deployment, including troubleshooting
7,300 + 2,100 columnsValidated classification backlog cleared
  • All four data engineers use the repository to change infrastructure across three regions.
  • Another engineer independently extended the grant abstraction, reducing reliance on the original author.
  • Replaced reviewer alerts that generated 34 mentions in 48 hours with consolidated notifications.

Ownership · Created the governance IaC repository and designed its dataset factory, multiregion layout, CI/CD and tier / IAM model. Incorporated a teammate's fix with authorship preserved. Final access decisions remained in the formal approval workflow.

5. Client on-premises-to-EMR on EKS PoC | Concentrix

08/2025 - 11/2025EMR on EKS · IRSA · Spot · Terraform · AirflowIndependent implementation
Client need

Client-specific on-premises YARN / Spark environments required repeated console work and manual setup. The PoC tested whether growing client demand could be served through reusable infrastructure, least-privilege access and workload-based cost models, rather than a one-off migration.

PoC target architecture

AirflowBatch orchestration
EMR on EKSSpark job runtime
IRSAPod-level least privilege
S3 · Spot nodesElastic data + compute

Decisions based on the workload

Compute

  • Chose EMR on EKS with Spot instead of an always-on cluster for batches concentrated into ~9 hours/day.
  • Configured Cluster Autoscaler to scale worker nodes during execution windows.
  • Separated the Airflow control-plane lifecycle from Spark workloads.

Security and reproducibility

  • Connected Service Accounts, IAM roles and custom policies through IRSA for per-Pod least privilege.
  • Used private EKS, a bastion and GitLab Runner to minimize external exposure.
  • Defined ~70 AWS / Kubernetes resources in Terraform and verified destroy-and-reapply deployment.

Cost comparison under consistent assumptions

ScenarioRelative monthly costAssumptions
Existing YARN cluster100: baselineSame workload; reservation-discount assumptions.
EMR on EKS + Spot~54: PoC modelElastic compute during batch windows only.
Limitations · The ~46% reduction is a PoC projection under matched workload and discount assumptions, not a before-and-after production bill. The project ended before production adoption because there was no authority to change existing client environments and no new deployment project.

Architecture practices

Requirements

Translated batch windows, security boundaries and repeated setup costs into acceptance criteria before selecting technology.

Architecture

Combined EMR on EKS, Spot, IRSA and Terraform into a reusable operating model.

Evidence boundaries

Separated PoC feasibility from production adoption, and projected savings from realized savings.
